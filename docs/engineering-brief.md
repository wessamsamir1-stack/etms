# ETMS — بريف هندسي شامل للمراجعة

**Enterprise Employee Transportation Management System**

منصّة متعدّدة المستأجرين (SaaS) لتخطيط وتشغيل وتتبّع رحلات نقل الموظفين اليومية.

A multi-tenant SaaS for planning, operating, and tracking daily employee-commute transport.

الوثيقة دي بتشرح كل جزء وطريقة عمله عشان تقدر تراجعه وتصطاد الأخطاء. آخر قسم (§10) مخصّص لمناطق المراجعة.

| | | | | | |
|---|---|---|---|---|---|
| **29** Migrations | **77** جدول | **94** Endpoint | **18** Route module | **116/116** اختبار | **12** محرّك مجال |

> **قاعدة الصدق:** «متحقّق» = اتنفّذ فعليًا على PostgreSQL 16 حقيقي. «مُراجَع» = اتكتب حسب المواصفة واتفحص ثابتًا بس ماتشغّلش (ينطبق على Flutter — مفيش SDK هنا).

## 01 — نظرة عامة · Overview

ETMS بيدير **الرحلات اليومية** لموظفي الشركات (مش تطبيق حجز مقاعد سياحي). كل شركة (tenant) لها بياناتها المعزولة تمامًا، بلغتين (عربي/إنجليزي)، وبإعدادات الكويت (KWD بثلاث خانات فلس، Asia/Kuwait، ‎+965، عطلة الجمعة/السبت).

- **الفلسفة:** بسيط، سريع، يومي. مفيش حجز مقاعد — بدلها **قائمة ركّاب (manifest)** بحالات حضور.
- **المال:** النظام **لا يحسب فلوس أثناء الرحلة** — بيسجّل الركوب والأيام فقط، والـ HR تقرّر الخصم لاحقًا.
- **الهدف:** آلاف الشركات، ملايين الرحلات شهريًا، عزل كامل بين الشركات.

**النموذج التشغيلي:** السائق يوصل نقطة التجمّع → مؤقّت انتظار (يحدّده الأدمن) → مين ركب/مين لأ (No-Show تلقائي) → الرحلة تكمل. كل ده متسجّل للتقارير.

## 02 — المعمارية والتقنيات · Architecture

**Clean Architecture:**

- **Domain** (بدون framework): محرّكات منطق نقية — أهلية، تكلفة، تحسين مسارات، manifest، تشفير، SSO، إشعارات. مُختبَرة بالوحدة.
- **App** (طبقة رفيعة): Fastify routes، تحقّق بـ `zod`، أخطاء `problem+json` (RFC 9457).
- **Data**: PostgreSQL 16 + PostGIS، وكل استعلام بيمرّ في سياق مستأجر (`Db.withTenant`).

**التقنيات:**

- **Backend:** TypeScript · Fastify v4 · PostgreSQL 16 + PostGIS.
- اعتماديات قليلة عمدًا: `fastify`, `pg`, `zod` + `@node-saml/node-saml` (للـ SAML فقط — لأن التحقّق من توقيع XML مايتكتبش بالإيد).
- **Frontend:** Flutter (سائق/موظف/أدمن) + كونسولين HTML شغّالين.

> ⚠️ **للمراجعة:** كل شغل الـ **backend/DB متحقّق منه فعليًا**. أما **Flutter فمُراجَع بصريًا فقط** (لم يُشغَّل) — دي أكبر فجوة تحقّق.

## 03 — نموذج الأمان · Security model (الأهم)

### عزل المستأجرين بـ Row-Level Security

كل جدول فيه `tenant_id` عليه سياسة RLS بـ **FORCE**. التطبيق بيتّصل بدور `etms_app_login` (**مش superuser**)، فحتى لو فيه خطأ في استعلام، قاعدة البيانات **فيزيائيًا** بتمنع قراءة بيانات شركة تانية. اللوكاب قبل الدخول بيتعمل عبر دوال `SECURITY DEFINER` بأقل صلاحية.

### 🔴 سطحان منفصلان تمامًا

- الـ **API العادي** بدور RLS (`etms_app_login`).
- الـ **Super-Admin platform API** بدور `BYPASSRLS` منفصل (`etms_platform_login`) عشان يشتغل عبر كل الشركات.
- توكن الشركة **مايقدرش** يوصل لمسارات المنصّة، والعكس. وجدول `platform_admin` **محجوب** عن دور التطبيق (تم التأكّد: `permission denied`).

| المجال | الآلية |
|---|---|
| المصادقة | JWT HS256 مخصّص · scrypt للباسورد · refresh token يتدوّر (single-use) · TOTP MFA للعمليات الحسّاسة |
| مقاومة التخمين | Rate-limit لكل IP + قفل تصاعدي لكل حساب (يشتغل حتى للحسابات الوهمية → مفيش تعداد إيميلات) |
| SSO | OIDC (Auth Code + PKCE، تحقّق JWKS) + SAML 2.0 (توقيع assertion عبر مكتبة معتمدة). لكل شركة إعدادها |
| PII عند التخزين | تشفير حقول AES-256-GCM (keyring قابل للتدوير) على عنوان السكن. مفتاح من env/KMS |
| نطاق الفرع (ABAC) | `scope_site_ids` يُصكّ في الـ JWT ويفلتر القراءة والكتابة لفروع الـ Branch Admin |
| التدقيق | سجل تدقيق ثابت (immutable) لكل شركة + سجل منفصل لأحداث المنصّة |

الصلاحيات مجموعات (RBAC)؛ المستخدم بياخد دور. القوالب النظامية (`tenant_id IS NULL`) بتتنسخ لكل شركة.

| الدور | الغرض | الحالة |

| **Company Admin** | مالك الشركة — كل صلاحيات المستأجر | ✅ |
| **Transport Admin** | تشغيل النقل: أسطول، سائقين، مسارات، dispatch | ✅ (30 صلاحية) |
| **HR Admin** | الموظفين والبيانات الرئيسية + مراجعة التسجيل | ✅ |

أدوار إضافية كقوالب: Operations Manager · Dispatcher · Finance · Vendor Manager · Auditor.

## 05 — الوحدات الوظيفية · Modules

### المصادقة و SSO

دخول بالباسورد + MFA، تدوير refresh tokens، تغيير باسورد يلغي الجلسات التانية.

SSO لكل شركة عبر OIDC و SAML — بيطابق الإيميل الموحّد بمستخدم موجود ويصكّ جلسة عادية (نفس الصلاحيات).

`login / OIDC / SAML` → تحقّق → `JWT (صلاحيات + نطاق)` → refresh يتدوّر

### الرحلة اليومية والـ Manifest

لكل رحلة قائمة ركّاب بحالات: `expected · on_the_way · boarded · no_show · excused · on_leave · removed`.

السائق يعلّم «وصل» (GPS أو زرّ) → مؤقّت انتظار (route → سياسة → 120ث افتراضي) → عند «غادر» يتسجّل المتبقّي **No-Show تلقائيًا**. «أنا في الطريق» ما بيوقفش العدّاد.

### باقي الوحدات

| الوحدة | طريقة العمل |
|---|---|
| **طلبات الرحلات** | الموظف يحدّد نقطة التقاط ويبعت لسائق محدّد أو بثّ للكل؛ أول سائق يقبل → الراكب يتضاف لـ manifest رحلته |
| **التتبّع اللحظي** | GPS pings → PostGIS. بثّ لحظي عبر SSE + Postgres LISTEN/NOTIFY مفلتر بالشركة. حوادث/SOS |
| **الاستخدام والخصم المؤجّل** | سجل ركوب (ما بيتحاسبش وقتها) → دفعة تصدير للخصم بـ idempotency وحماية MFA. أيام ومرّات فقط |
| **التسجيل الذاتي** | رقم وظيفي + سيلفي (مرجع) + OTP + مراجعة. الـ face-match حاليًا يدوي (port جاهز) |
| **الأهلية (AI-assisted)** | قواعد أولًا + وزن مخاطر → أخضر/أصفر/أحمر. وضع «ظل» مقابل «حي»، تجاوز يدوي، سياسة قابلة للتعديل |
| **الإشعارات (Worker)** | عامل مستقل يفرّغ صندوق `notification` عبر كل الشركات، يحلّ device token للـ push، يعيد بـ backoff. المزوّد الحقيقي محتاج مفاتيح |
| **منصّة الـ Super-Admin** | توفير شركات، اشتراكات/باقات، feature flags، سجل تدقيق — عبر دور BYPASSRLS. الميزات مُطبَّقة وقت التشغيل |
| **التقييم والمفقودات + White-label** | تقييم الرحلة، مفقودات، تاريخ الموظف/المركبة، علامة تجارية تُطبَّق وقت التشغيل |

## 06 — قاعدة البيانات · Data model

**29 migration** (V0000→V0028)، **77 جدول**، RLS على كل الجداول ذات `tenant_id`.

الهيكل التنظيمي:

`Company (tenant)` → `Brand` → `Branch (site)` → `Employees`

- **الأساس:** tenant, subscription, app_user, role, permission, user_role
- **التشغيل:** trip, trip_stop, trip_passenger, assignment, vehicle, driver, route
- **الجديد:** brand, tenant_feature, platform_admin, tenant_sso, tenant_saml, ride_request

> جداول قديمة اتشالت في التنظيف: `booking` و `seat_allocation` — الـ manifest بقى مصدر الحقيقة.

## 10 — مناطق تستاهل مراجعة دقيقة · Where to look for bugs

دي الأماكن اللي أنصحك تركّز عليها وقت المراجعة — نقاط قرار أو مخاطرة محتملة.

### 🔴 عزل المستأجرين على الجداول الجديدة — حرِج

أي جدول جديد فيه `tenant_id` لازم يتفعّل عليه RLS يدويًا (مش تلقائي). راجع إن `brand, tenant_feature, tenant_sso, tenant_saml, ride_request, trip_passenger` كلها عليها سياسة FORCE. وجداول المنصّة (`platform_admin`) لازم تفضل **محجوبة** عن دور التطبيق.

### 🔴 دور BYPASSRLS للمنصّة والـ worker — حرِج

`BYPASSRLS` صفة دور **ما بتتورّثش** بالعضوية — لازم تكون على دور الدخول نفسه. أي تسريب لبيانات اتصال المنصّة/الـ worker = تجاوز كل العزل. راجع إدارة الأسرار وصلاحيات الاتصالات دي.

### 🟡 ترقيم بارامترات SQL في نطاق الفرع — متوسط

في مصنع الـ CRUD، فلتر `scope_site_ids` والتحديث/الحذف بيبنوا فهارس بارامترات ديناميكيًا (`$n`). أي خطأ فهرس = فلتر غلط أو تسريب صف خارج النطاق. يستاهل قراءة سطر بسطر + اختبار حالة موظف في فرع تاني.

### 🟡 دلالات الـ lease في عامل الإشعارات — متوسط

الـ worker بياخد دفعة بـ lease ويبعت **خارج** المعاملة → **at-least-once**. يعني ممكن يتبعت الإشعار مرّتين لو كراش بعد الإرسال قبل التحديث. لو ده مش مقبول لقناة معيّنة، محتاج idempotency عند المزوّد.

### 🟡 إدارة مفاتيح تشفير الحقول — متوسط

التشفير AES-256-GCM سليم، بس **أمان المفتاح** هو كل شيء: لازم يجي من KMS/vault مش env في الإنتاج، والتدوير يحتفظ بالقديم للفكّ. من غير مفتاح = النص بيتخزّن واضح (passthrough) — تأكّد إنه متفعّل في الإنتاج.

### 🟡 مسار الـ SSE (hijack) — متوسط

ستريم التتبّع بيسيطر على الـ socket يدويًا (`reply.hijack`). راجع: تسريب اتصالات لو العميل قطع، إعادة الاتصال بعد سقوط الـ LISTEN، والتوكن في الـ query string (يظهر في اللوجز). الفلترة بالشركة هي حدّ العزل.

### 🟢 تقادم كاش الـ feature flags — منخفض

حالة الميزات مخزّنة ~30 ثانية. التبديل من نفس العملية بيمسح الكاش فورًا، لكن عبر عمليات متعددة التغيير بياخد لحد الـ TTL. **eventual consistency** — مقبول للـ flags.

### 🟢 Idempotency على عمليات الإنشاء — منخفض

مفيش مفاتيح idempotency على POST زي توفير شركة أو طلب رحلة — double-click/retry ممكن ينشئ صفّين. الـ slug المكرر محمي (409)، لكن التوفير عمومًا يستاهل idempotency key.

### 🟡 SAML/OIDC: الإعداد والأسرار — متوسط

إعداد كل شركة فيه `client_secret` / شهادة IdP. راجع: الأسرار مش بترجع في الـ GET، تُخزَّن مشفّرة في الإنتاج، والتحقّق من الـ audience/recipient/التوقيع فعّال. توقيع SAML بيتعمل بمكتبة معتمدة (مش يدوي) — ده صح.

### 🟡 Flutter غير مُجمَّع — متوسط

أكبر نقطة عدم-تحقّق: التطبيقات **ماتشغّلتش**. لازم `flutter analyze & test` وتسيير على جهاز قبل أي ثقة في طبقة العميل.
